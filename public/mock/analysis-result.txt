# 1. 개요

JavaScript와 같은 **동적 타입 언어**는 실행 시점까지 값의 구체적인 타입을 알기 어렵다는 특징이 있습니다. ^[#/text/1] ^[#/text/2]

정적 타입 언어에서는 컴파일러가 변수의 타입 정보를 활용하여 특정 타입에 최적화된 기계어를 생성할 수 있습니다. 반면 동적 언어에서는 동일한 연산이라도 실행 중에 서로 다른 타입의 값이 들어올 수 있기 때문에 보다 일반적인 코드를 생성해야 합니다. ^[#/text/3]

> 동적 타입 언어의 장점인 유연성을 유지하면서도 정적 타입 언어에 가까운 실행 성능을 얻는 방법은 무엇일까?

이 문서에서는 이러한 문제를 해결하기 위한 **Trace 기반 Just-In-Time(JIT) 컴파일** 방식과 타입 특수화의 개념을 살펴봅니다.

---

# 2. 왜 동적 언어의 최적화가 어려운가?

## 2.1 정적 타입 언어와의 차이

정적 타입 언어에서는 다음과 같이 변수의 타입이 컴파일 시점에 결정됩니다.

```ts
let count: number = 0

for (let i = 0; i < 1000; i++) {
  count += i
}
````

컴파일러는 `count`와 `i`가 숫자라는 정보를 알고 있기 때문에 숫자 연산에 특화된 기계어를 생성할 수 있습니다.

반면 JavaScript에서는 다음과 같은 코드가 가능합니다.

```js
let value = 10

value = 'hello'
value = true
value = { count: 10 }
```

하나의 변수에 여러 타입의 값이 할당될 수 있기 때문에 컴파일러가 **특정 타입만을 가정한 코드를 생성하기 어렵습니다.**

## 2.2 일반화된 코드의 문제

타입을 정확하게 알 수 없다면 런타임에서 다음과 같은 작업이 필요할 수 있습니다.

* 현재 값의 타입 확인
* 타입에 따른 연산 선택
* 객체 구조 확인
* 예외적인 타입 처리
* 적절한 런타임 함수 호출

이러한 검사는 프로그램의 실행 경로에 반복적으로 포함될 수 있습니다.

따라서 동적 언어에서는 다음 두 가지 목표 사이의 균형이 중요합니다.

1. **빠른 컴파일**
2. **효율적인 실행 코드**

---

# 3. Trace 기반 JIT 컴파일

Trace 기반 JIT 컴파일러는 프로그램 전체를 한 번에 최적화하지 않습니다.

대신 프로그램이 실제로 실행되는 과정을 관찰하고, **자주 실행되는 코드 경로를 찾아 해당 경로만 최적화**합니다.

## 3.1 실행 과정

일반적인 실행 흐름은 다음과 같습니다.

1. 프로그램을 바이트코드 또는 중간 표현으로 실행합니다.
2. 실행 횟수가 높은 코드 영역을 탐색합니다.
3. 자주 실행되는 루프를 **Hot Loop**로 판단합니다.
4. 해당 루프의 실행 경로를 기록합니다.
5. 실제로 관찰된 타입 정보를 수집합니다.
6. 수집한 정보를 바탕으로 특수화된 코드를 생성합니다.
7. 이후 동일한 경로가 실행되면 생성된 네이티브 코드를 사용합니다.

```text
JavaScript
    ↓
Bytecode Interpreter
    ↓
실행 프로파일 수집
    ↓
Hot Loop 탐색
    ↓
Trace 기록
    ↓
타입 특수화
    ↓
Native Code 생성
    ↓
최적화된 실행
```

---

# 4. Hot Loop란 무엇인가?

프로그램의 모든 코드를 동일하게 최적화할 필요는 없습니다.

실제 프로그램에서는 특정 코드 영역이 반복적으로 실행되는 경우가 많습니다. 특히 반복문 내부의 코드는 짧은 시간 동안 수천 번 또는 수백만 번 실행될 수 있습니다.

예를 들어 다음과 같은 코드가 있다고 가정해 보겠습니다.

```js
function calculate(numbers) {
  let total = 0

  for (let i = 0; i < numbers.length; i++) {
    total += numbers[i]
  }

  return total
}
```

위 코드에서는 다음 부분이 반복적으로 실행됩니다.

```js
for (let i = 0; i < numbers.length; i++) {
  total += numbers[i]
}
```

JIT 컴파일러는 이 영역이 충분히 자주 실행된다고 판단하면 해당 경로를 **Hot Trace**로 기록하고 최적화를 시도할 수 있습니다.

---

# 5. 타입 특수화

Trace가 기록될 때 컴파일러는 해당 경로에서 실제로 어떤 타입이 사용되었는지 관찰할 수 있습니다.

예를 들어 다음과 같은 실행이 반복되었다고 가정합니다.

```js
let total = 0

for (let i = 0; i < numbers.length; i++) {
  total += numbers[i]
}
```

관찰 결과:

| 값                | 관찰된 타입 |
| ---------------- | ------ |
| `total`          | Number |
| `i`              | Number |
| `numbers.length` | Number |
| `numbers[i]`     | Number |

이 경우 컴파일러는 해당 실행 경로에서 **Number 타입이 유지된다는 가정**을 세울 수 있습니다.

## 5.1 타입이 안정적인 경우

타입이 계속 동일하다면 일반적인 동적 타입 검사를 생략하고 보다 직접적인 연산을 수행할 수 있습니다.

```text
일반적인 실행

값 확인
  ↓
타입 검사
  ↓
연산 방식 결정
  ↓
실제 연산
```

최적화된 실행에서는:

```text
Number 타입이라고 가정
        ↓
바로 숫자 연산
        ↓
결과 저장
```

이러한 방식으로 반복적인 타입 검사의 비용을 줄일 수 있습니다.

---

# 6. Trace Tree

하나의 실행 경로만 항상 실행되는 것은 아닙니다.

다음과 같은 코드에서는 특정 조건에 따라 서로 다른 경로가 발생할 수 있습니다.

```js
for (const value of values) {
  if (typeof value === 'number') {
    total += value
  } else {
    handleOtherValue(value)
  }
}
```

처음에는 숫자 값만 관찰되었다고 하더라도 이후 문자열이나 객체가 등장할 수 있습니다.

이때 기존 Trace를 폐기하는 대신 새로운 실행 경로를 기록하여 **Trace Tree**를 확장할 수 있습니다.

```text
                 ┌─ Number Trace
Hot Loop ────────┤
                 └─ Other Value Trace
```

즉, 실행 중 새롭게 발견되는 경로를 점진적으로 추가할 수 있습니다.

---

# 7. 최적화가 항상 성공하는 것은 아니다

타입 특수화에는 중요한 전제가 있습니다.

> **과거에 관찰된 실행 패턴이 이후에도 유지되어야 한다.**

예를 들어 다음과 같은 코드가 있다고 가정합니다.

```js
function add(a, b) {
  return a + b
}
```

처음에는 다음과 같이 호출되었다고 가정합니다.

```js
add(10, 20)
add(30, 40)
add(50, 60)
```

컴파일러는 `a`와 `b`가 숫자라고 판단하고 숫자 연산에 특화된 코드를 생성할 수 있습니다.

하지만 이후 다음과 같은 호출이 발생한다면:

```js
add('hello', 'world')
```

기존의 타입 가정이 더 이상 유효하지 않습니다.

이러한 상황을 **Deoptimization**이라고 볼 수 있으며, 최적화된 코드를 빠져나와 보다 일반적인 실행 경로로 돌아갈 수 있습니다.

---

# 8. Trace 기반 접근 방식의 특징

**장점**

* 실제 실행 데이터를 기반으로 최적화할 수 있습니다.
* 자주 실행되는 코드에 컴파일 비용을 집중할 수 있습니다.
* 타입이 안정적인 루프를 효율적으로 특수화할 수 있습니다.
* 프로그램 전체를 분석하지 않아도 점진적인 최적화가 가능합니다.
* 중첩된 루프에서도 실행 경로를 단계적으로 확장할 수 있습니다.

**고려해야 할 사항**

* 실행 패턴이 자주 변경되면 최적화 효과가 감소할 수 있습니다.
* Trace를 기록하고 관리하기 위한 런타임 비용이 발생합니다.
* 잘못된 타입 가정은 Deoptimization으로 이어질 수 있습니다.
* 매우 많은 실행 경로가 발생하면 Trace 관리가 복잡해질 수 있습니다.

---

# 9. 기존 방식과의 비교

| 구분       | 전통적인 컴파일      | Trace 기반 JIT      |
| -------- | ------------- | ----------------- |
| 최적화 시점   | 주로 실행 전       | 실행 중              |
| 타입 정보    | 정적 정보 활용      | 런타임 정보 활용         |
| 최적화 단위   | 함수 또는 프로그램    | 실행 경로 및 루프        |
| 컴파일 비용   | 상대적으로 높을 수 있음 | 필요한 부분부터 점진적으로 수행 |
| 런타임 관찰   | 제한적           | 적극적으로 활용          |
| 동적 언어 대응 | 일반화된 코드 필요    | 실제 타입에 따른 특수화 가능  |

# 10. 전체 실행 흐름

전체적인 과정을 정리하면 다음과 같습니다.

1. **프로그램 실행**

   * 빠른 시작을 위해 인터프리터 기반으로 코드를 실행합니다.

2. **실행 정보 수집**

   * 어떤 코드가 반복적으로 실행되는지 관찰합니다.

3. **Hot Trace 발견**

   * 실행 횟수가 높은 루프와 경로를 식별합니다.

4. **Trace 기록**

   * 실제 실행된 명령과 타입 정보를 기록합니다.

5. **코드 특수화**

   * 관찰된 타입을 기반으로 최적화된 코드를 생성합니다.

6. **네이티브 코드 실행**

   * 이후 동일한 경로에서는 최적화된 코드를 사용합니다.

7. **새로운 경로 발견**

   * 기존 가정과 다른 타입이나 조건이 나타나면 새로운 Trace를 생성합니다.

8. **Deoptimization**

   * 기존 최적화 가정이 깨지면 일반적인 실행 경로로 되돌아갑니다.

---

# 11. 간단한 예제

다음 코드를 살펴봅시다.

```js
function sum(values) {
  let result = 0

  for (let i = 0; i < values.length; i++) {
    result += values[i]
  }

  return result
}
```

**초기 실행**

처음에는 인터프리터가 코드를 실행합니다.

```text
Interpreter
    ↓
sum()
    ↓
for loop
```

**반복 실행**

동일한 루프가 계속 실행되면서 실행 횟수가 증가합니다.

```text
loop count
  1 → 10 → 100 → 1,000 → 10,000
                          ↑
                      Hot Loop
```

**최적화**

컴파일러는 반복 실행 중 다음과 같은 패턴을 발견할 수 있습니다.

```text
result → Number
i      → Number
value  → Number
```

이를 바탕으로 해당 Trace를 숫자 연산에 맞게 특수화합니다.

---

# 12. 핵심 정리

Trace 기반 JIT 컴파일의 핵심 아이디어는 다음과 같습니다.

> **프로그램을 처음부터 완벽하게 분석하려고 하지 않고, 실제 실행에서 자주 나타나는 경로를 관찰한 뒤 해당 경로를 집중적으로 최적화한다.**

핵심 개념을 정리하면:

* **Hot Loop**: 자주 실행되는 반복 구간
* **Trace**: 실제 실행된 하나의 코드 경로
* **Type Specialization**: 관찰된 타입에 맞춰 코드를 최적화하는 과정
* **Trace Tree**: 여러 실행 경로를 연결하여 관리하는 구조
* **Deoptimization**: 최적화 가정이 깨졌을 때 일반 실행 경로로 돌아가는 과정
* **JIT Compilation**: 프로그램 실행 중 필요한 코드를 동적으로 컴파일하는 방식

# 13. 참고할 만한 질문

이 방식에서 자연스럽게 다음과 같은 질문이 이어집니다.

## Q1. 왜 모든 코드를 미리 컴파일하지 않는가?

동적 언어에서는 실행 전에 정확한 타입 정보를 알기 어렵기 때문입니다.

## Q2. Hot Loop는 어떻게 판단하는가?

실행 횟수 등의 런타임 프로파일 정보를 기반으로 특정 임계값을 넘는 코드를 Hot Code로 판단할 수 있습니다.

## Q3. 타입이 바뀌면 어떻게 되는가?

기존의 타입 가정이 깨지므로 최적화된 Trace에서 빠져나와 다른 실행 경로를 사용하거나 새로운 Trace를 생성할 수 있습니다.

## Q4. 그렇다면 JIT의 핵심은 무엇인가?

**실행 정보를 이용하여 자주 실행되는 코드에 컴파일 비용을 집중하고, 실제로 관찰된 타입과 실행 경로를 활용해 코드를 특수화하는 것**이라고 정리할 수 있습니다.

---

# 14. 결론

Trace 기반 JIT 컴파일은 동적 언어가 가진 유연성과 네이티브 코드 수준의 실행 성능 사이의 간극을 줄이기 위한 접근 방식입니다.

특히 **자주 실행되는 루프**, **안정적인 타입 정보**, **점진적인 Trace 생성**을 활용함으로써 전체 프로그램을 정적으로 분석하지 않고도 실행 중 중요한 부분을 선택적으로 최적화할 수 있습니다.

결국 이 접근 방식의 핵심은 단순합니다.

> **실제로 자주 실행되는 코드를 관찰하고, 실제로 관찰된 정보에 맞춰 빠르게 최적화한다.**
